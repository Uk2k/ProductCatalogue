# Persistence Foundation Design

## Purpose

Introduce the Product Catalogue data model and Entity Framework Core persistence boundary without adding API product operations, automated tests, or schema changes at application startup.

## Scope

This slice creates:

- The `Product` entity with a server-owned GUID identifier and the challenge-required `Name`, `Price`, and `Stock` properties.
- `AppDbContext` and SQL Server EF Core registration.
- Explicit entity mapping, including relational data-integrity constraints.
- A design-time factory for EF Core tooling.
- The first committed code-first migration that creates the `Products` table.
- A configuration contract for `ConnectionStrings:ProductCatalogue` that accepts User Secrets, environment variables, deployment variables, or a future Key Vault provider.

## Design

### Product Feature and Data Boundary

`Product` is a feature-owned entity at `Features/Products/Product.cs`. The shared persistence boundary is contained in `Data/`:

```text
Features/Products/Product.cs
Data/AppDbContext.cs
Data/Configurations/ProductConfiguration.cs
Data/AppDbContextFactory.cs
Data/ServiceCollectionExtensions.cs
Data/Migrations/<timestamp>_InitialCreate.cs
```

`Product.Id` is a `Guid` generated by the server when products are introduced in a later feature slice. The entity also contains `Name`, `Price`, and `Stock`.

`ProductConfiguration` maps the entity to `Products`, establishes `Id` as the primary key, makes `Name` required with a maximum length of 200, and maps `Price` to SQL Server `decimal(18,2)`. It adds SQL Server check constraints requiring `Price > 0` and `Stock >= 0`. These constraints are a final protection for data integrity; user-facing validation remains deferred to the create and update slices.

`AppDbContext` exposes `DbSet<Product> Products`. Startup calls `AddProductCataloguePersistence(IConfiguration)`, a focused registration method that configures EF Core with SQL Server.

### Configuration and Migrations

The repository contains no database credential or connection string value. The application requires configuration key `ConnectionStrings:ProductCatalogue`, which can be supplied locally through .NET User Secrets or environment variable `ConnectionStrings__ProductCatalogue`. Production deployment variables and a future Azure Key Vault provider will supply the identical configuration key.

`AppDbContextFactory` supports EF Core design-time commands by loading normal application configuration, optional .NET User Secrets, and environment variables. It loads User Secrets before environment variables so deployed configuration can override local values. It fails with a clear error when the connection string is missing, rather than silently using a development database.

An `InitialCreate` EF Core migration is committed to source control. Developers apply it explicitly with `dotnet ef database update`; the API never applies migrations automatically at startup. Future integration tests will apply the same migration to their disposable SQL Server database.

## Explicit Exclusions

- Minimal API product endpoints and MediatR handlers.
- FluentValidation and HTTP validation responses.
- Unit and integration test projects, Testcontainers, and database reset fixtures.
- Request logging middleware, error handling, and OpenTelemetry.
- Live Key Vault infrastructure or secret values.
- Automatic database migration at API startup.

## Acceptance Criteria

- The solution builds against .NET 8 with EF Core SQL Server dependencies.
- `Product` has GUID `Id`, `Name`, `Price`, and `Stock`.
- `AppDbContext` registers SQL Server using `ConnectionStrings:ProductCatalogue`.
- The initial migration creates the `Products` table with the configured fields, precision, and check constraints.
- `dotnet ef database update` can apply the migration when a connection string is externally supplied.
- No connection string, password, or Key Vault secret is committed.
- Application startup does not call `Database.Migrate()` or `Database.EnsureCreated()`.

## Verification

The implementation plan will verify compilation, inspect the generated migration, and run `dotnet ef database update` against a developer-supplied local SQL Server connection. Automated database verification is intentionally deferred to the next test-foundation slice.
